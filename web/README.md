# ICEPUNK licensing — Stages 1–3

A small Next.js App Router application for one private admin and manual invitations.
Includes buyer claiming, server activation and protected license/device management.
No desktop changes, fingerprint generation, offline tokens, signing, accounts or payments.
See [Stage 3 deployment/API/checklist](STAGE3.md) before upgrading.

## Run locally (Node.js 24)

In PowerShell:

```powershell
Set-Location -LiteralPath 'C:\Users\nikul\Desktop\iCEPUNKMIDIGENERATOR – копія\web'
npm ci
Copy-Item .env.example .env.local
npm run admin:credentials
```

The credential command generates a random admin password, its salted scrypt hash, and a random session secret.
Save the password in a password manager. Copy the printed hash and secret into `.env.local`; never put the password itself there.
This setup command intentionally prints credentials locally; do not share its terminal output.

Fill in the database connection string and keep `APP_ORIGIN=http://localhost:3000`. Then:

```powershell
npm run db:migrate
npm run dev
```

Open [http://localhost:3000/admin](http://localhost:3000/admin).
You are redirected to the login screen. Use `ADMIN_USERNAME` (default example: `admin`) and the generated password.
The invite form becomes available after login. If you use a different local port, update APP_ORIGIN and restart.

License types are initially `standard` and `beta`, labels only; neither grants different behavior in Stage 1.
Max devices defaults to 2 and accepts 1–20. Instagram usernames are normalized by removing a leading @ and lowercasing.

Creation displays a copyable `/claim/<token>` link exactly once. Send it privately to the intended buyer.
The buyer sees "Invite for @username", enters an email and claims a personal license.
The full key is returned once and has a Copy button. Reloading a used invite never reveals it again.
Email is syntax-validated but not verified; no email is sent. Common ASCII addresses and plus tags are supported;
quoted local parts and internationalized email addresses are not supported in this minimal form.

## Neon database

1. Create a Neon project and a PostgreSQL database (the default `neondb` is fine).
2. Use a separate development branch/database for local work. Do not point preview deployments at the production database.
3. In **Connect**, choose the correct branch, database and role; enable the pooled connection option and copy the PostgreSQL connection URL.
4. Set DATABASE_URL in `.env.local`. Preserve its SSL parameters (including `sslmode=require`); URL-encode any manually edited password.
5. Run `npm run db:migrate` from this folder. It connects using the Neon serverless HTTP driver.
6. Check the tables in Neon's SQL editor with `SELECT tablename FROM pg_tables WHERE schemaname = 'public';`.

The migration creates four business tables: invites, licenses, devices, feedback.
Two small infrastructure tables are also created:
- request_limits: one bounded row for shared login throttling.
- schema_migrations: applied migration name/checksum.

An unused invite has used_at = NULL. expires_at is nullable, allowing expiration support later.
Token hashes and license hashes are unique. licenses.invite_id is a required unique foreign key;
devices has a unique (license_id, device_id) pair. Licenses are created only through invite claiming.
Migration 002_activation.sql renames fingerprint to device_id (preserving uniqueness and rows),
adds last_seen_at and installs transactional activation/management functions. Apply it before Stage 3.
The initial migration is unchanged. No endpoint writes feedback yet.

The runner applies each pending numbered migration and its ledger entry in one transaction.
Running it again is a no-op; modifying an already-applied migration is rejected.
Run only one migration process at a time. Future changes should be new migrations, not edits to 001_initial.sql;
the runner discovers numbered SQL files in order. Procedural migrations use explicit
`-- statement-breakpoint` separators between top-level statements, keeping function bodies intact.
Do not apply the SQL manually and then run the runner: that bypasses its ledger.
DDL is never run during app requests or production builds.

Official guidance: [Neon connections](https://neon.com/docs/connect/connect-from-any-app),
[Neon serverless driver](https://neon.com/docs/serverless/serverless-driver).

## Environment variables

| Variable | Value |
|---|---|
| DATABASE_URL | Secret Neon PostgreSQL connection URL, including credentials and SSL parameters |
| APP_ORIGIN | Exact browser origin, no path or trailing slash; localhost for dev, HTTPS for production |
| ADMIN_USERNAME | Single admin username, e.g. admin |
| ADMIN_PASSWORD_HASH | scrypt:salt:hash value from npm run admin:credentials |
| ADMIN_SESSION_SECRET | Random 32-byte secret encoded as 64 hex characters, generated by the same command |

All variables are server-only. None use NEXT_PUBLIC.
There is no production fallback password or session secret; missing/invalid config blocks access.
Restart local development or redeploy after changing configuration.
The production build does not require a live DB, and does not apply migrations.

## Vercel

1. Import this Git repository into Vercel.
2. Set **Root Directory** to **web**, framework to **Next.js**, Node.js to **24.x**.
3. Use install command `npm ci` and build command `npm run build`; leave the output directory at the Next.js default.
4. Add the five variables above to **Production**. Set APP_ORIGIN to your exact HTTPS domain.
5. Before using the deployment, run the migration once against the production Neon database from a trusted machine.
   Use that database's DATABASE_URL for the command; never commit it.
6. Deploy and visit `https://your-domain/admin`.

Vercel detects Next.js directly; no vercel.json, custom server or additional backend is needed.
Choose a function region near the Neon database in Vercel settings.
For previews, either leave credentials unset (admin remains inaccessible), or use separate preview DB/credentials
and the exact preview URL as APP_ORIGIN. Do not expose production secrets to untrusted preview branches.
[Node.js 24 on Vercel](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions).

For a local production-mode server, `npm run build; npm start` requires an HTTPS APP_ORIGIN and an HTTPS reverse proxy.
Ordinary localhost testing should use `npm run dev`, which supports HTTP with a non-Secure development cookie.

## Checks

```powershell
npm test
npm run build
npm run test:http
npm audit --omit=dev
```

- Unit tests cover configuration, scrypt, session expiry/tampering/rotation, token randomness/hash, input limits and origin checks.
- Database integration tests run the actual migration and query functions against in-memory PostgreSQL via PGlite,
  a development-only dependency. They cover rollback/reapplication, constraints, stored hashes, invite creation and shared throttling.
- HTTP checks start and stop a local production Next.js server with temporary test credentials.
  They verify actual admin redirects/API authorization, CSRF, session tampering/expiry, input limits and logout cookie attributes.
  They do not require or modify a Neon database.
- Claim tests cover read-only GET, valid/invalid/expired/used invites, bad email, copied metadata,
  one-time keys, hash-only storage, concurrent service calls and rollback on insertion failure.
- PGlite serializes database access; its simultaneous-call test is not a multi-connection lock test.
  Set TEST_DATABASE_URL to an already-migrated dedicated Neon test branch and run
  `node --conditions=react-server --test tests/claim-neon.test.mjs` for 12 independent concurrent claims.
  The test is skipped without that explicit variable. It removes only its own invite/license fixture.
  Never use production for that opt-in test.

## Claim transaction and storage

The claim endpoint receives token/email as JSON under the same exact-origin and 2 KiB body protections as admin mutations.
It hashes the invite token, generates 16 random bytes on the server, and formats the license as
`ICEPUNK-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX` (32 uppercase hex characters / 128 random bits).
Only SHA-256 of the exact full key and its last four characters enter SQL. There is no recoverable encrypted copy.
The key is returned only after a successful database write, with no-store caching.
The browser holds it in component memory only; copying to the clipboard is an explicit buyer action.

One PostgreSQL statement uses a materialized SELECT ... FOR UPDATE to lock the invite,
then checks the locked row's used_at and expiry against clock_timestamp().
A data-modifying CTE marks the invite used and inserts the license from the returned metadata.
used_at is the claimed timestamp; licenses.created_at uses the same value.
All changes commit or roll back together. A competing claim waits for the lock, sees used_at,
and cannot insert another license. UNIQUE(licenses.invite_id) is a second safeguard.
Checking expiry after the lock also rejects an invite that expires while waiting.
There is no application-memory mutex and no multi-request read-then-write sequence.

The claim page is read-only. Used/expired/invalid states expose neither buyer email nor license metadata.
Only authenticated admin can see email, status, type, device allowance, claimed date and masked key suffix.
API status codes: 201 success, 400 invalid email, 404 invalid token, 409 used, 410 expired;
existing origin/body-size/configuration errors remain enforced.

## Manual browser checklist

Use a development Neon branch and keep APP_ORIGIN equal to your browser's exact origin.

1. Start the app, open /admin in a signed-out browser, and confirm it redirects to login.
2. Log in and create an invite for @producer, beta, max devices 3. Copy the link.
3. Open the link in a private browser window: see the username and email form.
   Refresh before submitting; no license should appear in admin/Neon yet.
4. Try an invalid email: no license is created. Enter a valid email and claim.
   Save/copy the one-time key, then refresh: see "This invite has already been claimed."
5. Refresh /admin: verify the email, beta, active, 3 devices, claimed date and masked suffix.
   The full key must not appear there.
6. Create another invite and open it in two tabs before claiming. Submit both:
   only one succeeds; the other reports already claimed. Verify one license for that invite.
   The automated Neon test is the stronger simultaneous-request check.
7. Modify one character in an invite URL: see the invalid state. No email/key is revealed.
8. For an expiration fixture, create a fresh test invite, find its UUID in Neon,
   and run the following SQL against that UUID only. Open or submit the invite: it must report expired.
9. Sign out; open /admin again and confirm no license metadata is accessible.

```sql
UPDATE invites
SET created_at = now() - interval '2 days',
    expires_at = now() - interval '1 day'
WHERE id = 'REPLACE_WITH_NEW_TEST_INVITE_UUID'
  AND used_at IS NULL;

SELECT i.instagram_username, i.used_at, l.email, l.license_type, l.status,
       l.max_devices, l.key_suffix, length(l.key_hash) AS hash_characters
FROM invites i LEFT JOIN licenses l ON l.invite_id = i.id
WHERE i.id = 'REPLACE_WITH_TEST_INVITE_UUID';
```

The expired fixture adjusts created_at only to satisfy the existing schema constraint
expires_at > created_at. Do not use this fixture SQL on buyer records.

## Security boundaries and deliberate simplifications

- A shared, environment-configured admin account; no users table, OAuth, password recovery or MFA.
- Password verification is server-side scrypt; a signed HttpOnly/SameSite=Strict cookie expires in eight hours.
  HTTPS production uses Secure and the __Host- prefix. Login and all mutations require the exact APP_ORIGIN.
  Every admin API checks its own authorization. Protecting the page alone is not considered sufficient.
- Logout clears the browser cookie. Stateless sessions have no per-session revocation list:
  a stolen cookie remains usable until expiry. Rotate the session secret or credentials and redeploy to invalidate all sessions.
- Global database-backed limit: 20 login attempts per 15 minutes, across all instances.
  This avoids trusting forwarded IP headers and adding Redis, but an attacker can temporarily lock out the owner.
  An owner can clear the single admin-login request_limits row in Neon if necessary.
- All database input uses parameters. JSON bodies are capped at 2 KiB; DB requests time out after 10 seconds.
  API errors are generic; request bodies, passwords, tokens and connection strings are not logged by application code.
- Invite tokens use 32 cryptographically random bytes. Only SHA-256 is stored.
  A lost creation response/link cannot be recovered; manually create a new invite.
  The old unused invite remains in the database. Invite deletion and claim recovery are not implemented.
- The server returns the raw invite only to the authenticated creator, with no-store caching.
  No analytics or third-party assets are loaded. The admin list never selects token hashes.
- One DB role is used for setup and runtime to keep configuration minimal; keep its credentials private and scope it to this project.
- A bearer invite can be claimed by whoever possesses the link; Instagram/email ownership is not verified.
- If the connection drops after the claim commits, the key may never reach the buyer.
  The invite remains claimed and the key cannot be recovered or reissued from that invite.
  Contact the seller; automated recovery/replacement is not implemented. Admin can revoke the old license.
- Next.js development access logging is disabled so it does not print full invite paths.
  Hosting/proxy access logs may still retain invite URLs: restrict their access/retention,
  and do not enable request-body logging or third-party analytics on claim pages.
- Public claim requests have body limits and unguessable tokens, but no dedicated bot/rate limiter.
  Admin login throttling is unchanged. Add hosting-level abuse protection if traffic warrants it.
- Server activation enforces device limits. Desktop integration and offline authorization are not implemented.
- Dependencies are pinned in package-lock.json. Keep security updates current.
